# 展馆欢迎平台

三端一体的展馆开放状态与导览系统：

| 端 | 入口 | 职责 |
|---|---|---|
| C 终端 | `/terminal.html?device=term-1` | 展示背景、开放时段、导览入口；离线用包内时间表本地计算 |
| 管理网页 | `/admin` | 编辑周历/节假日/临时事件/展区/路线，查看**实际生效范围**，发布与撤销 |
| 服务 API | `/api/*` | SQLite 维护发布版本与设备分组，实时状态计算，回执与审计 |

```bash
npm start          # http://localhost:8080 （/admin 管理页）
npm test           # 运行 7 组验收场景（18 项断言）
```

## 核心规则

**优先级**：临时事件（`priority` 高者优先，同级 `updated_at` 晚者优先）＞ 节假日 ＞ 常规周历。
管理端"生效时间线"与终端"今日时段"由**同一份代码**（`public/schedule.js`，UMD）解析，所见即所得。

**跨午夜**：会话表示为"开场日 + 分钟数"，`close_min` 可 >1440（如 1560=次日02:00）。
评估时刻 T 时同时展开 T 所在日期**与前一日期**的规则，前一日的会话溢出部分完整保留，
不会被简单按当天日期切断（验收场景 1：周六 01:30 仍属周五夜场）。

**路线-展区版本匹配**：路线保存 `zone_refs=[{zone_id, zone_version}]` 快照。展区任何变更
（改名/开关）都会 `version+1`；发布时静态校验，版本不符的路线标记不可用并注明原因；
终端在新鲜度内还会用包内事件**动态**复算（展区临时闭馆时入口关闭）。

**闭馆后旧页面不能引导进入**，三道防线：
1. 新鲜度内：包内含闭馆事件 → 终端本地评估即禁用导览按钮；
2. 超过 `valid_until`：进入"状态待核实"，导览全部禁用，只保留欢迎文字与基本导航；
3. 在线时：发布被撤销 → 包接口返回 `410 + 原因` → 终端立即降级为待核实。

## 提前下载带时间表的包 vs 服务端实时计算

| 维度 | 提前下载包（`/api/devices/:id/package`） | 服务端实时计算（`/api/status`） |
|---|---|---|
| 网络依赖 | 仅在同步窗口需要网络 | 每次判定都需要网络 |
| 一致性 | 包内快照，多台终端表现一致、可回放 | 永远最新，但两次询问之间可能变化 |
| 临时变更送达 | **只能等到下次同步**，包内看不到生成之后的事件 | 立即生效 |
| 时钟依赖 | 依赖终端本地时钟估算"现在"（会漂移） | 以服务器时钟为准 |
| 适用 | 大厅常显终端、网络不稳定、需离线运行 | 在线校验、管理端预览、回执核验 |

本系统终端默认"包模式 + 定期再校验"，可切换纯实时模式对比；两种模式共用同一解析函数，
因此**同一份数据必然算出同一个结果**，差异只来自数据新旧。

### 边界一：离线时钟漂移

终端估算当前时刻：`estNow = 包生成时刻 generated_at + 本地经过时长`。
- 设备晶振误差典型 ±20ppm（每天约 ±1.7 秒），离线越久误差越大，且**无法自我校正**；
- 用户/系统改钟、夏令时切换（场馆时区固定为 IANA 时区，不受影响；显示时区可切换）会直接污染估算；
- 后果：可能在闭馆后仍短暂显示"开放"，或提前进入"待核实"。
- **缓解**：以 `valid_until`（新鲜度期限）作为信任上限——漂移造成的误判被限制在
  新鲜度窗口内；超过窗口一律"状态待核实"，**不继续承诺开放**。更严格的部署可缩短
  新鲜度（如 2 小时）或使用带 NTP 的终端。

### 边界二：临时变更无法送达

离线期间新增的临时闭馆/开放事件，终端在下次同步前**无从知晓**：
- 若离线期间发生紧急闭馆，持有新鲜包的终端最多继续引导到 `valid_until` 为止；
- 因此新鲜度期限 = 运营方愿意承担的"信息滞后上限"，应在发布时按场馆风险设定；
- 在线再校验（默认 20 秒）是主要补救：一旦发现发布被撤销或被新版本取代，立即降级。

## 数据与留痕

- **发布版本**：整体快照（周历/节假日/事件/展区/路线/背景/欢迎语）+ `valid_from/valid_until`；
  新发布使旧版本 `superseded`，全部分组自动滚动；分组也可钉住指定版本。
- **撤销必须填原因**：`revoke_reason/revoked_by/revoked_at` 入库并写审计，永久可追踪；
  被撤销发布不再下发（410），引用它的分组回退到最新有效发布。
- **并发**：临时事件乐观锁（`version` + `base_version`），冲突返回 409 与当前值，
  冲突尝试本身也写入审计（谁、基于哪个过期版本、想改成什么）。
- **回执**：`receipt_id` 幂等去重；晚到不拒绝——核验"开始时刻该发布是否有效、路线是否可用、
  场馆是否开放"，标记 `late` 与 `valid_at_start` 并留痕。
- **审计**：发布、撤销（含原因）、冲突、晚到回执、分组指派全部入 `audit_log`。

## 验收场景（test/acceptance.js）

1. 时区切换：显示时区可切，开闭馆判定永远按场馆时区；跨午夜不被日期切断
2. 优先级：临时事件＞节假日＞周历，同级事件按 priority
3. 两人同时改临时事件：409 冲突 + 留痕 + 基于最新版本重试成功
4. 设备离线跨日：超过新鲜度 → 状态待核实，欢迎文字与基本导航保留，导览禁用
5. 背景文件失败：回退备用纯色背景并提示（终端可用 `?bgbreak=1` 演示）
6. 旧导览回执晚到：幂等接受、late 标记、重复提交去重
7. 路线-展区版本匹配；撤销发布 → 终端 410 → 待核实，旧页面不再引导进入

## 已知简化

- 墙钟→UTC 换算在夏令时缝隙（不存在的本地时刻）可能偏差一个偏移量；场馆时区
  Asia/Shanghai 无夏令时，不受影响。
- sql.js 为 WASM 版 SQLite，写操作防抖落盘；生产可换 better-sqlite3/PostgreSQL，接口不变。
- 终端离线期间的回执补交在 UI 中仅提示，未实现本地队列。
